# dnn_exp37_hrf_tuned_20260824 — HRF 超参补救（warmup + 降 LR），架构判定前的必经检验

- **Date**: 2026-08-24  **Cost**: G4 flex ~$15（1.0M 局 @ ~40 games/s ≈ 7h）  **Status**: launching
- **触发**：用户质疑"大模型是不是只是需要更多局数"。核查发现两个问题：
  1. **exp36 发射时漏传 `--warmup_updates`（warmup=0）**——我的失误；exp30 用了 150，
     而代码自身 help 文本写明 "transformers in RL want ~1000"。两条 HRF 线都严重欠 warmup。
  2. 但主症状不是欠训练而是**优化不稳**：同 LR 1e-4 下 HRF 后段 approx_kl 0.016–0.020，
     是 cnn_m/handset（0.0055–0.0057）的 **3 倍**；Elo 在相邻检查点（间隔 5 万局）
     甩动 ±100（exp36: 910/795/874/899/855/816/898），exp30 从 460k 到 962k 横盘 50 万局。
     **震荡形状 ≠ 缓慢爬升形状**——继续喂局数只会继续震荡。
- **反证**：handset（20M 参数，同代码同预算）收敛正常（1.0M→2.0M 稳步 1017.5→1031.1，KL 0.0057）。
  所以不是"大模型天然慢"，是 HRF 这条线超参没调对。

## Method
`hrf_xl_v4`，恒定 `--entropy_coef 0.01`（沿用 exp36 中已证优于 schedule 的熵机制），
**新增 `--warmup_updates 1000`（代码推荐值）+ `--lr 5e-5`（步长减半，针对 3× KL 的稳态过冲）**，
`--bf16_infer --amp_update`（已验证 1.63–1.8× 提速），1.0M 局。
对照：exp36（同架构同熵机制，warmup 0 / lr 1e-4，1.81M 局 → T1 896.2）。

## Success Criteria
1. **优化健康（主判据）**：后段 approx_kl 落到 ≤0.008（接近 cnn/handset 的 0.0055 量级）；
   ladder 相邻点波动收窄到 ≤±40（vs exp36 的 ±100）。
2. **Elo**：1.0M 处 T1 > 896.2（exp36 用 1.81M 局达到的水平）→ 证明此前是超参问题而非架构上限。
   若 ≥1000 则 HRF 重回候选；若仍 ~880 且 KL 已降到健康区间 → **架构上限判定才成立**。
3. 若 1.0M 处仍在爬升（ladder 末段斜率显著正），追加预算续训而非当场判死。
