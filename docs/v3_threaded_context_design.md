# v3 设计：串联上下文（事件流）架构

> 状态：设计稿（2026-08-02），未立项实施。当前三臂对照（PBRS / PPO / 价值 bundle）
> 在 v2 单步架构上跑完后，v3 作为下一个大版本。
> 动机讨论与决策记录：本文档 + SKILLS.md。

## 1. 动机

v2 架构每个决策是独立单轮对话（π(a|当前观测)，历史全部外化到观测字符串），带来三个结构性限制：

1. **意图不持久**：跨巡承诺型策略（染手、国士等高番路线）没有载体——每步都要从
   手牌重新推导计划。这是稀有役学习的根本障碍之一（另一半是采样密度）。
2. **观测残缺**：prompt 的公共段只列对手牌河，**自家牌河缺失**——模型无法自察振听
   风险、无法基于自己的弃牌史做防守推理（v2 已确认此缺口）。
3. **时序信息被聚合抹掉**：牌河是集合视图，"谁在谁立直后第一时间打了什么"这类
   读牌信号丢失。

串联上下文（LLM 长程 agent RL 的主流范式）原生解决全部三项。

**成本侧修正**（推翻早期反对论据）：增量事件编码下，一局全程 ≈ 4–6k token
（初始 ~400 + 每决策轮 ~40 增量 + ~80 生成 × ~35 轮），2B 模型可承受；
"串联会到 3 万 token" 的估算错在假设每步重渲染全量状态。

## 2. 事件流协议（rollout 与语料共用）

每个座位一条对话线程。POMDP 安全：线程内只包含该座位可见的信息
（公共事件 + 自己的私有摸牌/手牌）。

```
[system]  角色 + 输出格式要求（与 v2 相同的 <think>/<action> 契约）
[user]    <初始状态>：与 v2 相同的完整状态渲染（手牌/局况/供托/宝牌指示）
[assistant] <think>…</think><action …/>                    ← 决策 1
[user]    事件增量，例：
          「下家打 3s。对面碰 3s 后打 8p。你摸到 5m。
            合法动作：…」                                   ← 只含增量 + 合法动作
[assistant] <think>…</think><action …/>                    ← 决策 2
[user]    「上家打 7z（你可以碰）。合法动作：碰/过」          ← 中断询问同样入流
[assistant] <think>…</think><action type="skip"/>
…
```

设计要点：
- **事件词表**：`摸牌(私)`、`打牌`、`副露(碰/吃/杠+来源)`、`立直宣言`、`翻新宝牌`、
  `荣和/自摸(终局)`、`流局`。渲染为紧凑中文短句，与 v2 状态语言一致。
- **合法动作列表**每轮必附（v2 约定不变，格式合规的锚点）。
- **状态快照重注入**（抗小模型长程归纳失败）：每 N=6 个自己的决策轮，在增量后附
  一次完整状态重渲染。N 是 v3 的第一个消融变量（N=∞ 即纯事件流）。
- **上限保护**：context 超过 8k token 时从最老事件截断（保留 system + 最近快照后
  的全部内容）。预期正常对局不触发。

## 3. SFT 语料（v3 格式）

- 教师对局引擎不变；`generate_sft_data.py` 增加 `--threaded` 模式：每局每座位输出
  **一条**多轮对话样本（而非 ~55 条单轮样本）。
- 忠实 CoT 原则不变，且升级：教师在路线切换点（如同色 ≥7 张转染手）把**计划**写进
  think（「转清一色路线，此后弃字牌与他色」），后续轮的 think 可引用前文计划——
  这是 v2 做不到的"意图持久化"示范。
- 规模：300 局 × 4 视角 = 1200 条对话，约 6M token（与 v2 语料同量级）。
- loss 只算 assistant span（多轮 SFT 标准做法，chat_format.py 需支持多轮 mask）。

## 4. 训练（RL）

- **Loss masking**：一局一序列，只对 assistant token 计损失。
- **Span 级 advantage**：决策 k 的 span 内所有 token 共享 advantage_k
  （= 该步 return-to-go 归一化后截断，v2 语义不变）。实现：flatten 时输出
  (序列, [span 起止], [advantage_k])，PPO/REINFORCE 的 mask 从"单段"变"多段"。
- **PPO**：old_logprobs 在 rollout 逐轮生成时按 span 记录（与 v2 相同的
  raw-logits 约定）；ratio/clip/approx-KL 逐 token，与 v2 的 ppo.py 复用
  （ppo_clip_loss 本就是 [B,T]+mask 接口，天然支持多段 mask，无需改动）。
- **PBRS 奖励不变**：Φ 是状态函数，与 context 形态无关；potential/potential_value
  直接复用（解析器需从事件流恢复手牌，或让引擎在轨迹里直接附带手牌快照——推荐后者，
  砍掉正则解析这层脆弱性）。
- **结算分发不变**：每座位线程的最后一个 span 加 settlement。

## 5. Rollout 调度

两阶段实施：

- **v3.0（务实）**：保持无状态批量——每决策轮把该座位的**全线程**重新 prefill。
  实测外推：5k prefill 批量下 ~0.3s/序列（A100 compute-bound），24 路并发下
  prefill 总开销 ≈ 决策轮 ~7s，可接受；decode 吞吐与 v2 相同（335 tok/s @ bf16 B=24）。
  批量调度器（batch_rollout.py）只改 prompt 构建（线程累积器），调度逻辑复用。
- **v3.1（优化）**：per-game KV 持久化 + 增量 prefill。需要 paged/continuous
  batching（自研或引入 vLLM 做 rollout 服务）。仅当 v3.0 的 prefill 开销实测
  成为瓶颈时立项。

## 6. 迁移与兼容

| 资产 | v3 处置 |

| 引擎（table.py 规则/结算） | 不变；新增事件发射接口（step 返回结构化事件而非仅状态串） |
| PBRS 奖励（rewards.py） | 不变（解析层改为吃引擎快照） |
| ppo.py | 不变 |

| 监控/GCS/多 VM 基建/WebUI | 复用；WebUI 解析层适配事件流 |

## 7. 风险与消融

1. **2B 长程归纳能力**：散落历史 vs 工程化摘要。消融：快照重注入周期 N ∈ {∞, 6, 3}。
2. **训练/推理错位**：多轮 SFT 与逐轮 rollout 的模板必须逐 token 一致
   （v2 的 69.5% 格式合规事故是前车之鉴——冒烟必须先验证格式合规 ≥95%）。
3. **截断策略**：截断触发时的分布外风险；先测正常对局 token 分布再定上限。
4. **对照性**：v3 首个 run 与 v2 最优臂同 seed 同预算对照，成功标准沿用
   scale-free 四条 + 新增「染手/高番出现率」探针。
