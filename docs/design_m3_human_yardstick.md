# M3：人类校准标尺入池（Mortal）——可行性核查与集成设计

2026-08-21，用户批准 Mortal 作为人类标尺（仅测量，训练永不接触）。

## 核查结论
- **官方权重不公开**（作者 2022-08 声明：为防在线作弊"无计划释出"，仅提供 mjai.ekyu.moe 在线复盘服务）。
- **社区权重可得**：Hugging Face `VoidShine/mortal-298k`——ResNet 192ch×40blk，训练数据为
  2025-2026 天凤高段四人半庄牌谱，AGPL-3.0；自述强度：mjai.ekyu.moe 相似度 83-92%、
  雀魂 MAKA 测试平均 S+ 级（声明"不建议用于排位"）。**这是一个真实的人类高手级标尺**
  （天凤高段牌谱蒸馏+RL），满足 M3 需求。
- 接口：mjai 协议（JSON 事件流）+ libriichi（Rust 模拟器，Python 绑定，40K 半庄/小时）；
  官方评估框架支持 Mortal vs Mortal / vs akochan / vs 日志引擎。
- 备选 akochan：README 抓取失败（404），但 Mortal 官方评估链内置 akochan 对手，可作第二标尺。

## 纯度声明
标尺只出现在 Elo 评分池（冻结对手），训练 rollout 永不采样它；不从它蒸馏、不用它的评估做奖励。
它的作用仅是把「人类高手水平」变成可判定的刻度。

## 集成方案（两条路，M2 后择一）
A. **把我们的 agent 接进 mjai 世界**：写一个 mjai bot 包装器（我们的 encoder 从 mjai 事件流重建
   桌面状态 → 网络出动作 → 回 mjai 动作 JSON），在 libriichi/mjai 模拟器里与 Mortal 对打。
   优点：用对方成熟的评估框架和规则实现；难点：规则差异（我们单副结算 vs 半庄；东风/场风随机化；
   我们引擎的细节规则如 4 杠上限）需对表，否则评分不可比。
B. **把 Mortal 接进我们的引擎**：写 mjai 事件生成器（我们的 table 状态 → mjai 事件流喂给
   Mortal 的 libriichi 推理）作为 arena 的一个 policy。优点：评分协议（复式配对、Elo 池）不变、
   与全部历史读数可比；难点：必须保证事件流语义与 Mortal 训练分布一致（牌河顺序、立直宣言、
   副露表示等），任何偏差会系统性削弱 Mortal 而高估我们。
**倾向 B**（保持标尺与既有 Elo 池同尺），并用 A 做一次交叉校验（在 Mortal 主场打一组，
确认两边给出的相对强度一致）——交叉一致才算标尺合格。

## 规则/设定差异（必须在判定前对表）
单副 vs 半庄顺位、赤宝牌有无、场风/自风随机化、流局听牌费、包牌、4 杠规则。
差异处以「对 Mortal 无系统性不利」为准则处理；无法消除的写入标尺的诚实声明。

## 预算
集成工程 ~1-2 天（本地），评估本地 CPU/4080 即可；无云成本。
